# Development Instructions for Fuel50

> Guidelines for Java/Spring development in the Fuel50 microservices platform.

## 🎯 Project Overview

- **Type**: Reactive microservices platform
- **Tech Stack**: Java 21, Spring Boot 3.3+ WebFlux, R2DBC, MySQL
- **Architecture**: 6 independent services + 3 shared libraries
- **Paradigm**: Non-blocking I/O, reactive streams (Mono/Flux)

---

## 🏗 Architecture Pattern

**Microservices with Reactive Programming**:
- Each service is independent (user, company, action, activity, rating)
- Shared libraries for DTOs and client communication
- Non-blocking I/O throughout with Project Reactor (Mono/Flux)
- R2DBC for async database access

### Service Structure
```
{service-name}/
├── controller/    # REST endpoints, request/response handling
├── service/       # Business logic
├── repository/    # Database access (R2DBC)
├── model/         # Entities
└── exception/     # Custom exceptions
```

---

## 📂 Naming Conventions

**Packages**: `com.fuel50.{service}.{layer}`
- Example: `com.fuel50.user.controller.UserController`

**Classes**:
- Controllers: `{Entity}Controller` (e.g., `UserController`)
- Services: `{Entity}Service` (interface), `{Entity}ServiceImpl`
- Repositories: `{Entity}Repository` (interface extends `ReactiveCrudRepository`)
- Models: `{Entity}`, `{Entity}Entity` (e.g., `User`, `UserEntity`)
- DTOs: `{Entity}DTO`, `{Entity}Request`, `{Entity}Response`
- Exceptions: `{Specific}Exception` (e.g., `UserNotFoundException`)

**Methods**:
- Reactive: Return `Mono<T>` or `Flux<T>`
- Getters: `get{Field}()` → returns `{Field}`
- Finders: `findBy{Criteria}()` → returns `Mono<Entity>` or `Flux<Entity>`

## 🤖 Instructions for AI Agents

### ✅ DO's

1. **Use Reactive Types Everywhere**
   - Return `Mono<T>` for single values, `Flux<T>` for multiple
   - Example: `Mono<User> findById(Long id)`

2. **Extend ReactiveCrudRepository**
   - Automatic reactive methods: `findById()`, `save()`, `deleteById()`
   - Custom methods return `Mono<T>` or `Flux<T>`

3. **Use @Transactional for Transactions**
   - Marks transactional boundaries
   - Automatic rollback on exception

4. **Map DTOs at Service Boundary**
   - Convert Entity → DTO before returning from controller
   - Use `.map()` in reactive chain

5. **Handle Errors with Mono.error()**
   - Throw custom exceptions from services
   - @ControllerAdvice maps to HTTP responses

6. **Use Constructor Injection**
   - Inject repositories and clients in controller/service constructors
   - No @Autowired on fields

7. **Apply @RestController at Service Boundary**
   - Only controllers expose REST APIs
   - Services and repositories are internal

8. **Test with Reactor Test & Testcontainers**
   - `Mono/Flux.test()` for reactive testing
   - Real MySQL container for integration tests

### ❌ DON'Ts

1. **Don't Use Blocking Calls**
   - ❌ `thread.sleep()`, `.block()`, `Stream.forEach()`
   - ✅ Use reactive operators: `.flatMap()`, `.map()`, `.subscribe()`

2. **Don't Mix Sync and Async**
   - ❌ Regular `List<T>` alongside `Flux<T>`
   - ✅ Stay in reactive world with Flux/Mono

3. **Don't Leak Framework Types**
   - ❌ Return `Mono` from services (leak implementation detail)
   - ✅ Services return DTOs, controllers handle Mono wrapping

4. **Don't Create New Threads**
   - ❌ `.subscribeOn(Schedulers.io())` without reason
   - ✅ Let framework manage threading

5. **Don't Ignore Subscription**
   - ❌ Create Mono/Flux but don't subscribe
   - ✅ Controllers always subscribe (framework does this)

6. **Don't Use Traditional ORM Methods**
   - ❌ `session.save()`, `.list()` (blocking)
   - ✅ Use R2DBC reactive repositories

## 🔄 Common Development Workflows

### Adding a New Service

1. **Create service directory** under `apps/`
2. **Create controller** with REST endpoints returning `Mono/Flux`
3. **Create service** with business logic
4. **Create repository** extending `ReactiveCrudRepository`
5. **Create models** as JPA entities
6. **Add DTOs** to `common-dtos`
7. **Create HTTP client** in `common-clients` if called by other services
8. **Write tests** with Reactor test and Testcontainers

### Adding an Endpoint

```java
@GetMapping("/{id}")
public Mono<UserResponse> getUser(@PathVariable Long id) {
    return userService.findById(id)
        .map(userMapper::toResponse);
}
```

### Service-to-Service Call

```java
// In CompanyService, call UserService
@Autowired
private UserServiceClient userClient;

public Mono<CompanyWithUsers> getCompanyWithUsers(Long companyId) {
    return companyRepository.findById(companyId)
        .flatMap(company -> 
            userClient.getUsersByCompanyId(companyId)
                .collectList()
                .map(users -> new CompanyWithUsers(company, users))
        );
}
```

## 🚫 Forbidden Practices

### 1. Blocking Operations
```java
// ❌ BAD
Mono<User> user = userRepository.findById(1L).block();

// ✅ GOOD
return userRepository.findById(1L);
```

### 2. Imperative Instead of Declarative
```java
// ❌ BAD
List<User> users = new ArrayList<>();
userRepository.findAll().subscribe(u -> users.add(u));
return users;

// ✅ GOOD
return userRepository.findAll().collectList();
```

### 3. Global State
```java
// ❌ BAD
public static UserService userService;

// ✅ GOOD
@Autowired
private UserService userService;  // Constructor injection preferred
```
